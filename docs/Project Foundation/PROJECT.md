\# 1. Executive Summary



WeatherApp is a modern, production-quality weather application built using the latest React ecosystem and professional software engineering practices.



The objective is not simply to display weather information, but to demonstrate how modern frontend applications are designed, architected, tested, deployed, documented, and maintained in a real software engineering environment.



This project intentionally follows enterprise development workflows including Git Flow, Pull Requests, Continuous Integration, automated testing, documentation-driven development, and modular architecture.



The repository should resemble a real production application rather than a tutorial project.

\# 7. Project Principles



Every contribution must satisfy the following principles.



\## Simplicity



Choose the simplest solution that satisfies requirements.



Avoid unnecessary abstractions.



\---



\## Maintainability



Code should be understandable after months without explanation.



\---



\## Reusability



Duplicate code should be avoided.



Shared behavior belongs inside reusable components, hooks, or utilities.



\---



\## Scalability



Structure should support future features without large refactoring.



\---



\## Consistency



Naming, architecture, styling, and code organization must remain consistent across the project.



\---



\## Accessibility



Accessibility is mandatory.



Keyboard navigation must work.



Interactive elements require labels.



Color contrast must meet accessibility guidelines.



\---



\## Performance



Avoid unnecessary renders.



Avoid unnecessary API calls.



Lazy-load when appropriate.



Optimize bundle size.

\# 9. Project Architecture Goals



The application should be organized around features and reusable components.



Business logic should never be tightly coupled to presentation.



Components should remain small and focused.

API communication should be centralized.



Configuration should remain isolated.

\---



\# 11. Mandatory Rules



The following rules are non-negotiable.



\## Code Quality



Always use TypeScript.



Never use the any type unless absolutely unavoidable.



No unused code.



No commented-out production code.



\---



\## Components



Reusable first.



Avoid duplication.



Keep components focused.



\---



\## Styling



Tailwind utilities only.



No inline styles.



No duplicated utility combinations.



\---



\## API



All API communication must pass through the service layer.



Components must never directly call external APIs.



\---



\## Git



Every feature requires its own branch.



Never commit directly to main.



Never merge without CI passing.



\---



\## Testing



Every important feature requires tests.



Broken tests block merging.



\---



\## Documentation



Documentation must be updated whenever architecture or workflows change.



\---



\# 12. Best Practices



Prefer composition over inheritance.



Prefer pure functions.



Prefer reusable hooks.



Keep functions short.



Use descriptive naming.



Handle loading states.



Handle empty states.



Handle error states.



Write self-documenting code.



Review your own code before opening a Pull Request.



\---



\# 13. Common Mistakes



Avoid:



\- Massive components

\- Large files

\- Copy-pasted code

\- Inline API requests

\- Hardcoded values

\- Magic numbers

\- Missing loading UI

\- Missing error UI

\- Ignoring accessibility

\- Ignoring responsive design

\- Mixing business logic with presentation

\- Ignoring TypeScript errors

\- Disabling ESLint rules without justification
